# 微前端升级可行性评估

## 1. 评估结论

采用“Vue 3 主应用 Shell + Vue 3 业务子应用 + Vue 2 Legacy 子应用”的微前端架构，整体可行性较高，适合当前 DSCP 管理后台明确要求最终重构升级到 Vue 3 及以上的目标。

该架构应满足以下前提：

- Vue 3 主应用只承载认证、权限、菜单、主路由、Layout 和子应用治理等平台能力；
- Vue 3 与 Vue 2 子应用作为主应用的同级子应用，不形成多层嵌套；
- 新业务只允许进入 Vue 3 子应用；
- Vue 2 作为有明确退出期限的 Legacy 应用，只维护存量功能；
- 主子应用之间通过正式协议通信，不共享 Vue 实例、Router 实例或 Store 实例；
- 子应用按业务域拆分，不按单个页面或组件过度拆分。

| 评估项 | 结论 |
| --- | --- |
| 技术可行性 | 高 |
| 与当前项目适配度 | 中高 |
| Vue 2 退出路径 | 清晰 |
| 新模块开发体验 | 较好 |
| 初期基础设施成本 | 较高 |
| 长期维护成本 | 可控 |
| 是否推荐 | 推荐，但必须控制拆分粒度 |

## 2. 当前项目基础

当前项目采用完整的 Vue 2 技术体系：

| 技术 | 当前版本或现状 |
| --- | --- |
| Vue | 2.6.12 |
| Vue Router | 3.4.9，Hash 模式 |
| Vuex | 3.6.0 |
| UI 组件库 | Element UI 2.15.x |
| 构建工具 | Vue CLI 4.4.6、Webpack 4 |
| SFC 编译器 | vue-template-compiler 2.6.12 |
| 全局能力 | 大量 `Vue.prototype`、`Vue.use()` 和全局组件 |
| 页面承载 | Vue 2 `router-view`、`keep-alive`、动态路由 |

现有系统对 Vue 2 Runtime、Element UI、Vuex 和全局插件依赖较深，不适合在同一个 Bundle 中直接混编 Vue 2、Vue 3 SFC。通过独立构建的微前端边界隔离两套运行时，更符合渐进迁移要求。

## 3. 推荐目标架构

```text
Vue 3 主应用 Shell
├── 登录与 Token 生命周期
├── 用户、权限和商户上下文
├── Layout、一级菜单和标签页
├── 浏览器主路由
├── 全局消息、异常和监控
├── 子应用注册、加载、更新和卸载
│
├── Vue 3 订单子应用
├── Vue 3 物流子应用
├── Vue 3 财务子应用
│
└── Vue 2 Legacy 子应用
    ├── 未迁移业务页面
    ├── Vue Router 3
    ├── Vuex 3
    └── Element UI
```

所有子应用必须直接挂载到主应用：

```text
推荐：Vue 3 Shell
      ├── Vue 3 子应用 A
      ├── Vue 3 子应用 B
      └── Vue 2 Legacy 子应用

禁止：Vue 3 Shell
      └── Vue 3 子应用
          └── Vue 2 子应用
```

## 4. 主应用与子应用职责

| 能力 | Vue 3 主应用 | Vue 3 子应用 | Vue 2 Legacy |
| --- | --- | --- | --- |
| 登录与退出 | 负责 | 消费上下文 | 消费上下文 |
| Token 生命周期 | 负责 | 不独立维护 | 不独立维护 |
| 用户和权限 | 提供 | 消费 | 消费 |
| 一级菜单 | 负责 | 提供元数据或不参与 | 不再维护独立菜单 |
| 主路由 | 负责 | 只负责内部路由 | 只负责遗留内部路由 |
| Layout | 负责 | 不重复建设 | 逐步移除旧 Layout |
| 标签页 | 负责 | 通知路由变化 | 通知路由变化 |
| 全局消息 | 提供统一服务 | 调用 | 通过桥接调用 |
| 业务 API | 不负责 | 负责本业务域 | 负责存量业务 |
| 业务状态 | 不保存 | Pinia 或组件状态 | Vuex 3 |
| 业务组件 | 不提供 | Vue 3 组件体系 | Vue 2 组件体系 |
| 子应用生命周期 | 负责调度 | 实现 | 实现 |

主应用必须保持轻量，不应包含订单、物流等业务接口、业务表格、业务枚举或子应用专属组件。

## 5. 子应用拆分粒度

| 拆分方式 | 示例 | 评价 |
| --- | --- | --- |
| 按组件拆分 | 每个弹窗一个应用 | 禁止，粒度过小 |
| 按页面拆分 | 每个列表一个应用 | 不推荐，治理成本高 |
| 按一级菜单拆分 | 订单、物流、财务 | 推荐 |
| 按稳定业务域拆分 | 履约、售后、库存 | 推荐 |
| Vue 2 统一为一个 Legacy | 全部未迁移页面 | 迁移初期推荐 |

适合独立子应用的业务域通常具备独立菜单、明确 API 边界、相对独立状态以及独立发布价值。只有一两个简单页面且与其他模块频繁共享页面状态时，不宜独立拆分。

## 6. Vue 2 Legacy 改造要求

当前 Vue 2 项目不能原封不动嵌入，需要先完成“去壳化”：

| 当前能力 | 改造方向 |
| --- | --- |
| Layout、Sidebar、Navbar | 子应用模式下不渲染，由主应用接管 |
| TagsView | 由主应用统一管理 |
| 登录页 | 迁移到 Vue 3 主应用 |
| Token | 由主应用传入和更新 |
| 权限菜单 | 主应用生成，Legacy 只处理页面内权限 |
| Router | 只保留 Legacy 内部路由 |
| Vuex | 只保留存量业务状态，不继续扩张 |
| 全局消息 | 短期保留，逐步切换到主应用服务 |
| 全局监听器 | 挂载和卸载必须成对处理 |

Legacy 子应用应实现标准生命周期：

```js
export async function mount(container, context) {
  // 创建并挂载 Vue 2 实例
}

export async function update(context) {
  // 更新 Token、权限、商户等上下文
}

export async function unmount() {
  // 销毁 Vue 实例、请求、路由监听和全局事件
}
```

## 7. 路由方案

浏览器 URL 应由 Vue 3 主应用统一拥有：

| 路径 | 所属应用 |
| --- | --- |
| `/orders/*` | Vue 3 订单子应用 |
| `/logistics/*` | Vue 3 物流子应用 |
| `/finance/*` | Vue 3 财务子应用 |
| `/legacy/*` | Vue 2 Legacy 子应用 |

路由流转：

```text
浏览器 URL
  → Vue 3 主路由识别业务域
  → 加载对应子应用
  → 把剩余子路径交给子应用 Router
```

当前 Vue 2 项目使用 Hash Router，不应让主应用与 Legacy 同时修改同一个 `location.hash`。Legacy 可采用内存路由、独立路径前缀或由主应用传入当前子路径。

## 8. 主子应用通信协议

主应用向子应用提供稳定上下文：

```ts
interface AppContext {
  token: string
  baseApi: string
  user: UserInfo
  permissions: string[]
  merchantId?: string
  locale: string
  route: string
}
```

子应用实现统一生命周期：

```ts
interface SubApplication {
  mount(container: HTMLElement, context: AppContext): Promise<void>
  update(context: AppContext): Promise<void>
  unmount(): Promise<void>
}
```

允许的跨应用事件包括：

- 路由变化；
- Token 失效；
- 退出登录；
- 标题和标签页变化；
- 全局消息提示；
- 打开其他业务域页面。

禁止双方互相访问 Vue 实例、组件 ref、Router 实例、Vuex 或 Pinia 实例，也不应通过 `window` 暴露大型全局 Store。

## 9. 状态管理

| 状态 | 归属 |
| --- | --- |
| Token、当前用户、全局权限 | 主应用 |
| 当前语言和主题 | 主应用 |
| 当前商户上下文 | 主应用或正式共享服务 |
| 订单业务状态 | 订单子应用 |
| 物流业务状态 | 物流子应用 |
| Legacy 页面状态 | Legacy Vuex |
| 标签页和主导航 | 主应用 |

不得建立横跨所有应用的超级 Store。Vue 3 子应用使用自己的 Pinia，Vue 2 Legacy 继续使用 Vuex；跨应用状态通过上下文快照、事件或正式共享服务同步。

## 10. 共享代码边界

推荐建立框架无关共享包：

```text
packages/
├── contracts       # 类型和通信协议
├── api-core        # HTTP 基础能力
├── shared-utils    # 纯函数
├── design-tokens   # 颜色、间距和层级
└── vue3-ui         # 仅供 Vue 3 应用使用
```

| 内容 | Vue 2/3 能否共享 |
| --- | --- |
| API 契约和类型 | 可以 |
| 常量和枚举 | 可以 |
| 日期、金额、集合纯函数 | 可以 |
| Design Token | 可以 |
| Vue SFC | 不可以直接共享 |
| Element UI/Element Plus 组件 | 不可以 |
| Router 实例 | 不可以 |
| Vuex/Pinia Store | 不可以 |
| Vue 3 UI 组件包 | 仅 Vue 3 应用共享 |

## 11. CSS 与浮层风险

Element UI 与 Element Plus 都大量使用 `.el-*` 类名，样式冲突属于最高风险项之一。

| 风险 | 处理建议 |
| --- | --- |
| `.el-*` 相互覆盖 | 为 Legacy 和 Vue 3 子应用建立样式边界 |
| 全局 Reset 污染 | 只允许主应用提供基础 Reset |
| Dialog 挂载到 `body` | 每个子应用指定 Overlay 容器 |
| `z-index` 冲突 | 主应用定义统一层级协议 |
| Legacy 全局 SCSS | 逐步限制在 Legacy 根节点下 |
| 图标、字体重复加载 | 统一资源策略或严格隔离 |

可按项目情况采用 CSS 前缀、样式沙箱或 Shadow DOM。Shadow DOM 隔离较强，但弹窗、下拉框等 Teleport/Overlay 组件需要额外验证。

## 12. 依赖共享策略

| 策略 | 优点 | 风险 | 建议 |
| --- | --- | --- | --- |
| Vue 3 子应用独立打包 Runtime | 隔离稳定 | 包体积增加 | 初期推荐 |
| Vue 3 应用共享 Runtime | 减少重复体积 | 版本必须严格兼容 | 稳定后评估 |
| Vue 2 与 Vue 3 共享 Runtime | 无法实现 | Runtime 不兼容 | 禁止 |
| 所有第三方依赖全部共享 | 包体积小 | 升级互相阻塞 | 不推荐 |

迁移初期应优先保证隔离性，不应过早为了包体积强制共享 Vue 3、Router、Pinia 或 Element Plus Runtime。

## 13. 部署与运行治理

| 部署方式 | 优点 | 缺点 | 建议 |
| --- | --- | --- | --- |
| 主子应用独立部署 | 发布解耦 | 版本协调复杂 | 成熟阶段推荐 |
| 所有产物统一部署 | 运维简单 | 发布互相绑定 | 初期可用 |
| 运行时远程加载 | 独立性高 | 需要加载失败治理 | 稳定后采用 |
| iframe | 隔离最高 | 通信和体验较差 | 高风险 Legacy 页面备用 |

必须建立子应用版本、资源清单、加载超时、失败页面、缓存、回滚和兼容矩阵。

## 14. 迁移阶段

| 阶段 | Vue 3 主应用 | Vue 3 子应用 | Vue 2 Legacy |
| --- | --- | --- | --- |
| 1. 建立底座 | Shell、认证、菜单、路由 | 试点一个低风险模块 | 承载全部旧页面 |
| 2. 稳定协议 | 通信、异常、监控、标签页 | 开发查询和 CRUD 模块 | 完成去壳化 |
| 3. 按域迁移 | 保持轻量 | 按业务域增加 | 路由持续减少 |
| 4. 收敛共享层 | 稳定公共服务 | 承载主要业务 | 只剩复杂模块 |
| 5. 退出 Vue 2 | 删除 Legacy 注册 | 承载全部业务 | 下线 |
| 6. 架构清理 | 清理兼容层 | 按需要独立或合并 | 不存在 |

初期建议只有一个 Vue 2 Legacy 子应用和一个 Vue 3 试点子应用，待通信、路由、样式和部署机制稳定后再增加业务子应用。

## 15. 防止过度设计

| 错误倾向 | 后果 |
| --- | --- |
| 每个页面一个子应用 | 发布和运行时治理过于复杂 |
| 主应用包含业务逻辑 | 形成新的大型单体 |
| 共享一个全局 Store | 子应用失去隔离性 |
| 所有 Vue 3 依赖强制共享 | 子应用无法独立升级 |
| Vue 2 继续新增业务和公共组件 | Legacy 永远无法退出 |
| 建设跨 Vue 2/3 UI 组件库 | 维护成本极高 |
| 多层子应用嵌套 | 路由、卸载和错误边界复杂 |
| 没有 Vue 2 下线指标 | 微前端变成永久双栈 |

## 16. Vue 2 退出指标

| 指标 | 目标 |
| --- | --- |
| Vue 2 新增页面 | 0 |
| Vue 2 新增公共组件 | 0 |
| Legacy 路由数 | 持续下降至 0 |
| Legacy 活跃业务模块 | 持续下降至 0 |
| Vuex 遗留模块 | 下降至 0 |
| Element UI 使用 | 下降至 0 |
| `Vue.prototype` 依赖 | 下降至 0 |
| Vue 2 专属依赖 | 下降至 0 |
| Legacy 构建产物 | 最终删除 |

## 17. 主要风险及建议

| 风险 | 等级 | 建议 |
| --- | --- | --- |
| Element UI 与 Element Plus 样式冲突 | 高 | 优先完成样式和 Overlay PoC |
| Hash Router 所有权冲突 | 高 | 主应用统一拥有浏览器 URL |
| Legacy 无法完整卸载 | 高 | 建立监听器、请求和实例销毁检查 |
| Token 和权限状态不同步 | 高 | 使用可更新的正式上下文协议 |
| 子应用拆分过细 | 中高 | 仅按稳定业务域拆分 |
| 主应用业务化 | 中高 | 主应用代码评审限制业务依赖 |
| 多应用发布不兼容 | 中 | 建立版本兼容矩阵和回滚方案 |
| 重复 Runtime 增加资源开销 | 中 | 架构稳定后再优化共享依赖 |

## 18. 最终建议

| 决策项 | 建议 |
| --- | --- |
| 主应用 | Vue 3 轻量平台 Shell |
| Vue 3 子应用 | 按业务域拆分 |
| Vue 2 子应用 | 单一 Legacy 应用 |
| 子应用层级 | 全部直接挂载到主应用 |
| 新业务 | 只允许进入 Vue 3 子应用 |
| 全局能力 | 主应用服务或框架无关共享包 |
| 状态 | 主应用全局状态 + 子应用业务状态 |
| 路由 | 主应用拥有 URL，子应用负责内部路由 |
| 初期部署 | 可统一部署，成熟后按需独立 |
| Vue 2 退出 | 使用路由数、依赖数和构建产物持续衡量 |

总体结论：Vue 3 主应用同时承载 Vue 3 业务子应用和 Vue 2 Legacy 子应用，既能隔离两套 Runtime，又能让新业务直接进入目标技术栈，并通过逐路由替换实现 Vue 2 有序退出。对当前 DSCP 管理后台而言，该方案具有较高可行性，但成功与否取决于主应用保持轻量、路由所有权统一、样式隔离可靠、生命周期可完整卸载，以及 Vue 2 下线指标得到持续执行。
