# 组件开发可行性参考

## 一、结论

建议组件库从项目初期采用：**单一组件契约 + 共享无框架内核 + Vue 2/Vue 3 双适配层**。

不建议把目标设为“一份 `.vue` 文件同时兼容 Vue 2 和 Vue 3”。更现实的“不重复开发”是：业务逻辑、数据模型、校验、设计 Token、基础样式和测试用例只开发一次，Vue 2/Vue 3 各自保留很薄的渲染适配层。

## 二、推荐总体架构

| 层级 | 包名示例 | 主要职责 | 是否依赖 Vue |
|---|---|---|---|
| 组件契约 | `@dscp-ui/contracts` | Props、事件参数、插槽、公开方法、数据类型 | 否 |
| 共享内核 | `@dscp-ui/core` | 校验、格式化、状态机、查询构建、选项映射 | 否 |
| 设计变量 | `@dscp-ui/tokens` | 颜色、间距、字号、圆角、层级、CSS Variables | 否 |
| 基础样式 | `@dscp-ui/styles` | BEM 样式、布局、状态样式、动画 | 否 |
| Vue 2 适配层 | `@dscp-ui/vue2` | Vue 2 Options API、Element UI 适配 | 是 |
| Vue 3 适配层 | `@dscp-ui/vue3` | Vue 3、Element Plus 适配 | 是 |
| Vue 2 演示项目 | `playgrounds/vue2` | 验证当前项目接入和兼容性 | Vue 2 |
| Vue 3 演示项目 | `playgrounds/vue3` | 从项目初期持续验证未来迁移 | Vue 3 |

建议目录：

```text
dscp-ui/
├── packages/
│   ├── contracts/
│   ├── core/
│   ├── tokens/
│   ├── styles/
│   ├── vue2/
│   └── vue3/
├── playgrounds/
│   ├── vue2/
│   └── vue3/
├── docs/
├── package.json
└── package-lock.json
```

组件库可以采用独立仓库，通过 npm workspaces 管理，不必和当前业务项目放在同一个仓库。

## 三、不建议一套 Vue 源码兼容两个版本的原因

| 差异点 | Vue 2 | Vue 3 | 推荐处理方式 |
|---|---|---|---|
| `v-model` | `value` + `input` | `modelValue` + `update:modelValue` | 适配层转换 |
| UI 框架 | Element UI | Element Plus | 分别封装 |
| 属性和事件透传 | `$attrs`、`$listeners` 分离 | 统一进入 `$attrs` | 适配层处理 |
| 插槽 API | `$scopedSlots` 等 | 统一 Slots API | 保持对外插槽名称一致 |
| Render API | Vue 2 `h` 参数模式 | Vue 3 VNode API | 分开实现 |
| 生命周期 | `beforeDestroy` 等 | `beforeUnmount` 等 | 分开实现 |
| 第三方组件实例 | Element UI 实例 | Element Plus 实例 | 禁止暴露到公共 API |

强行共用一份 SFC 往往会产生大量版本判断，复杂组件的维护成本可能比两个薄适配组件更高。

不建议把 `vue-demi` 作为新组件库的核心兼容方案。其官方仓库已明确表示不建议新项目继续使用，并计划逐步弃用。

## 四、最大化复用的方法

```text
@dscp-ui/core
    └── 查询、选项转换、缓存、校验、默认值处理
             ↓
@dscp-ui/vue2                    @dscp-ui/vue3
Element UI 渲染                  Element Plus 渲染
value/input                     modelValue/update:modelValue
```

两个版本应向业务项目提供相同的组件名称和使用语义：

```vue
<dscp-business-select
  v-model="form.businessId"
  :disabled="readonly"
  clearable
  @change="handleBusinessChange"
/>
```

| 契约类型 | 统一要求 |
|---|---|
| Props | 名称、默认值、必填性和业务语义一致 |
| Events | 事件名称、参数顺序和数据结构一致 |
| Slots | 插槽名称和插槽参数结构一致 |
| Methods | `open()`、`close()`、`validate()` 等公开方法一致 |
| 样式 | 统一采用 `dscp-*` 类名前缀和 CSS Variables |
| 数据结构 | 不返回 Vue Observable、组件实例等版本相关对象 |
| 异常行为 | 校验失败、请求异常和空数据表现一致 |

## 五、不同组件的共享程度

| 组件类型 | 示例 | 推荐策略 | 预计共享程度 |
|---|---|---|---:|
| 纯逻辑 | 校验器、格式化、权限判断 | 全部放入 `core` | 100% |
| 设计系统 | Token、图标、基础 CSS | 独立于 Vue | 90%–100% |
| 简单展示组件 | 状态标签、金额、空状态 | 共享契约和样式，双适配 | 80%–90% |
| 表单组件 | 业务选择器、日期范围 | 共享数据逻辑，分别渲染 | 60%–80% |
| 弹窗/抽屉 | 编辑弹窗、详情抽屉 | 共享状态和契约，分别适配 UI 库 | 50%–70% |
| 复杂表格 | 搜索表格、虚拟列表 | 共享列模型和查询逻辑，视图双实现 | 40%–70% |
| 页面私有组件 | 页面专属业务区域 | 留在业务项目中 | 不进入组件库 |

“不重新开发”不应理解为模板代码一行不重复，而应理解为核心业务能力、交互契约和设计系统不重新设计与实现。

## 六、依赖与构建设计

| 项目 | 建议 |
|---|---|
| Vue 依赖 | 放在对应包的 `peerDependencies` |
| Element 依赖 | Vue 2 包依赖 Element UI；Vue 3 包依赖 Element Plus |
| 打包外置 | Vue、Element UI、Element Plus 不打入组件库产物 |
| 模块格式 | 至少输出 ESM；考虑当前 Webpack 4 项目时同时输出 CJS |
| 样式 | 提供独立 CSS 入口，不强制通过 JavaScript 注入 |
| 类型 | 输出 `.d.ts`；契约包优先使用 TypeScript |
| 按需加载 | 使用命名导出，避免默认全局注册 |
| 完整安装 | 可额外提供 `Vue.use()` 和 `app.use()` 插件入口 |
| 版本管理 | Vue 2/Vue 3 包尽量保持相同版本号和变更记录 |
| 发布方式 | 推荐发布为两个独立 npm 包 |

Vue 2 包的依赖示例：

```json
{
  "peerDependencies": {
    "vue": "^2.6.12",
    "element-ui": "^2.15.0"
  }
}
```

Vue 3 包应独立声明 Vue 3 和 Element Plus 的 peer dependency 范围。

## 七、建议的项目启动顺序

| 阶段 | 工作内容 | 验收条件 |
|---|---|---|
| 1. 定义边界 | 明确哪些组件进入组件库、哪些留在业务项目 | 不把页面业务逻辑塞进公共组件 |
| 2. 建立契约 | 定义 Props、Events、Slots、Methods | Vue 2/Vue 3 API 对齐 |
| 3. 建立 Token | 从现有项目提取颜色、间距、字号等变量 | 不直接依赖 Element 内部变量 |
| 4. 建立共享内核 | 抽离校验、转换、状态管理等纯逻辑 | `core` 不引用 Vue |
| 5. 建立双适配包 | 同时创建 `vue2`、`vue3` 包 | 两个包均可独立构建 |
| 6. 建立双 Playground | 创建 Vue 2、Vue 3 示例项目 | 同一组件在两端行为一致 |
| 7. 开发试点组件 | 选择三种复杂度的组件 | 发现兼容问题并修正架构 |
| 8. 接入当前项目 | 使用本地压缩包或内部 npm 仓库验证 | 不通过源码别名直接耦合 |
| 9. 建立测试矩阵 | 单元、契约、视觉和打包测试 | 两端行为持续一致 |
| 10. 正式发布 | SemVer、变更日志、迁移说明 | 业务项目可以按版本升级 |

首批建议试点：

| 组件 | 验证目标 |
|---|---|
| `DscpStatusBadge` | Token、样式和简单 Props |
| `DscpBusinessSelect` | `v-model`、异步选项和事件一致性 |
| `DscpConfirmDialog` | 弹窗、插槽、公开方法和 UI 框架差异 |

不要一开始迁移几十个组件，应先通过三类试点验证架构，再批量建设。

## 八、开发红线

| 规则 | 原因 |
|---|---|
| `core`、`contracts` 禁止导入 Vue | 保证真正跨版本复用 |
| 公共 API 禁止暴露 Element 实例类型 | 避免业务代码绑定 UI 框架 |
| 禁止在公共样式中大量覆盖 `.el-*` 内部类 | Element UI/Plus DOM 结构不同 |
| 公共组件必须同时定义 Vue 2/Vue 3 契约 | 避免未来重新设计 API |
| 稳定组件发布前必须通过双 Playground | 尽早发现版本差异 |
| 插槽、事件和公开方法必须有测试 | 编译通过不代表行为一致 |
| 业务接口请求默认不放进基础组件 | 避免组件和当前系统强耦合 |
| 默认按需导出，不自动全局注册 | 保持依赖清晰并支持 tree-shaking |
| 组件样式统一使用命名空间 | 避免子应用和 UI 库之间样式冲突 |
| Vue 2 仅作为过渡支持目标 | Vue 2 已结束官方支持，不能成为长期架构核心 |

## 九、测试矩阵

| 测试类型 | Vue 2 | Vue 3 | 重点 |
|---|---:|---:|---|
| 共享内核单元测试 | 共用 | 共用 | 校验、转换、状态逻辑 |
| 组件契约测试 | 必须 | 必须 | Props、事件、插槽、公开方法 |
| 视觉回归 | 必须 | 必须 | 两端视觉和交互差异 |
| UI 框架兼容测试 | Element UI | Element Plus | 弹窗、表单、表格、浮层 |
| 打包导入测试 | Webpack 4 | Vite | ESM/CJS、CSS、按需导入 |
| 样式冲突测试 | 必须 | 必须 | 命名空间、主题和子应用隔离 |

## 十、方案对比与最终意见

| 方案 | 评价 |
|---|---|
| 只开发 Vue 2 组件，以后再迁移 | 不推荐，未来仍会集中返工 |
| 一份 SFC 同时编译 Vue 2/Vue 3 | 不推荐，复杂组件兼容成本高 |
| 全面采用 Web Components | 不推荐作为后台组件库默认方案 |
| Vue 2/Vue 3 组件库完全独立开发 | 可行，但重复成本过高 |
| **共享内核、单一契约、双 Vue 适配层** | **推荐，最符合当前使用和未来升级目标** |

最终结构应明确为：

> `@dscp-ui/vue2` 服务当前项目，`@dscp-ui/vue3` 服务未来项目；二者共享 `contracts + core + tokens + styles`。Vue 2 最终可以被删除，但共享内核和 Vue 3 组件继续保留。

该方案会产生少量必要的 Vue 渲染层重复，但能够避免未来重新开发组件的业务能力，并为 Vue 3 迁移留下清晰的退出路径。
